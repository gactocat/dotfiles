# チームメンバー活動レポート

エンジニアリングマネージャーが 1on1 や期末の人事考課に使うための、メンバーの活動内容レポートを作成する。GitHub・Slack・Google Drive・esa・Notion の 5 サービスを横断して活動の証跡 (evidence) を収集し、リンク付きの Markdown レポートにまとめる。

## 原則

このレポートは人の評価に関わる文書である。以下を必ず守ること。

- **事実と解釈を区別する**。収集したログから言えること (事実) と、そこからの示唆 (解釈) を書き分ける。解釈には「〜と考えられる」など推測であることが分かる表現を使う。
- **すべての主張に evidence リンクを付ける**。PR、Slack メッセージ、ドキュメントなど、原典への URL を必ず併記する。リンクのない定性的な主張は書かない。
- **網羅性の限界を明記する**。このレポートは業務システム上に記録が残る活動しか拾えない。口頭でのサポート、DM、権限外のドキュメントは見えない。レポート末尾に必ず制約事項を記載する。
- **ネガティブな断定をしない**。「活動が少ない」ように見えても、それは可視データ上の話にすぎない。課題点は「対話で確認したい点」として提示する。

## 入力の確認

作業を始める前に次の 2 つを確定させる。

1. **対象メンバー**: 名前を受け取ったら `roster.local.md` (このスキルと同じディレクトリ) を確認する。各サービスの ID が揃っていればそれを使う。ファイルがなければ `roster.example.md` を参考に作成する。ID がなければ「メンバー ID の解決」に従って解決する。
2. **対象期間**: 開始日と終了日を YYYY-MM-DD で確定させる。「上期」「下期」などの期間表現は会社の会計年度に依存するため、曖昧な場合は具体的な日付範囲をユーザーに確認する。

## メンバー ID の解決

同一人物でもサービスごとに ID が異なる。初出のメンバーは以下で解決し、結果を `roster.local.md` に追記して次回以降に使い回す。`roster.local.md` は公開リポジトリへコミットしない。

| サービス | ID の種類 | 解決方法 |
| --- | --- | --- |
| GitHub | ユーザー名 | `gh search prs --owner=<github-org> --author=<候補>` で実在確認。不明なら対象 org の PR から氏名で推測しユーザーに確認 |
| Slack | ユーザー ID (U...) | `slack_search_users` で氏名検索 (ツールは ToolSearch でロード) |
| Google Drive | メールアドレス | 組織のメール規約 (例: `xxx@example.com`)。不明ならユーザーに確認 |
| esa | screen_name | `esa_list_posts` で氏名や推測 screen_name を検索して確認 |
| Notion | ユーザー名 / UUID | `notion-get-users` で検索 |

`roster.local.md` の形式:

```markdown
| 名前 | GitHub | Slack | Email | esa | Notion |
| --- | --- | --- | --- | --- | --- |
| 山田 太郎 | taro-yamada | U01234ABCDE | taro.yamada@example.com | taro_yamada | taro-yamada |
```

解決した ID が本人のものか確信が持てない場合は、収集を始める前にユーザーに確認する。別人のデータを混ぜるのが最悪の失敗である。

## 事前チェック

収集を始める前に利用可能性を確認する。

- **GitHub**: `gh auth status` が通ること。
- **Slack / Google Drive / Notion**: MCP ツールを ToolSearch でロードできること。
- **esa**: esa MCP は認証切れになっていることがある。ツールが使えない場合は、ユーザーに claude.ai のコネクタ設定 (またはインタラクティブセッションの /mcp) での認証を依頼し、esa をスキップしてレポートに「esa は未収集」と明記するか、認証後に再実行するかを選んでもらう。

一部サービスが使えなくても中断しない。使えるサービスだけで収集を進め、欠けたサービスをレポートの制約事項に明記する。

## 収集手順

サービスごとの具体的な収集方法は references/ 配下に分かれている。**収集を始める前に、対象サービスの reference を必ず読むこと**。

- [references/github.md](references/github.md) — PR・レビュー・コミット・Issue。`scripts/github.sh` で定量データを一括取得できる。対象 GitHub org を引数で指定する
- [references/slack.md](references/slack.md) — 発言の傾向、注目スレッド、他者支援
- [references/google-drive.md](references/google-drive.md) — 設計書・議事録などのドキュメント作成
- [references/esa.md](references/esa.md) — 記事の投稿・更新
- [references/notion.md](references/notion.md) — ページ作成・編集 (制約が多いので best-effort)

収集のコツ:

- 期間が長い (3 か月以上) 場合、全メッセージ・全ドキュメントを読もうとしない。まず定量値と一覧を取り、影響の大きそうなもの (コメントの多い PR、長い設計ドキュメント、障害対応スレッド) を 5〜10 件深掘りする。
- 深掘り対象を選んだら、その活動が「何の課題を解決したのか」「誰に影響したのか」を原典から読み取る。これが定性ハイライトの材料になる。
- 複数サービスにまたがる同一の仕事 (例: 設計 doc → PR → リリース告知) は 1 つのハイライトに束ねる。サービス別の羅列より仕事単位の物語のほうが考課の材料として役立つ。

## レポートの作成

収集が終わったら以下のテンプレートでレポートを書く。保存先はデフォルトで `~/Documents/activity-reports/<メンバー名ローマ字>-<開始日>-<終了日>.md` (ディレクトリがなければ作る)。ユーザーが別の場所を指定したらそちらに従う。

文章は CLAUDE.md の Markdown 整形ルール (和欧文間スペース、水平線禁止、見出しに通し番号を付けない) に従う。

```markdown
# <名前> 活動レポート (<開始日> 〜 <終了日>)

作成日: <今日の日付> / 作成方法: AI (Claude) による業務システム上の活動ログの収集・要約

## サマリ

<この期間の活動を 3〜5 文で要約。最も大きな成果と活動の傾向>

## 定量サマリ

| 項目 | 値 | 備考 |
| --- | --- | --- |
| マージされた PR | n 件 | うち主要リポジトリ: ... |
| レビューした PR | n 件 | |
| コミット | n 件 | |
| esa 記事 (新規/更新) | n / n 件 | |
| Google Drive ドキュメント | n 件 | 作成または主要編集 |
| Notion ページ | n 件 | 把握できた範囲 |
| Slack 発言の傾向 | | 主要チャンネルと概況。厳密な件数より傾向を書く |

## 定性ハイライト

<影響の大きかった仕事を 3〜7 件。それぞれ: 何をしたか / なぜ重要か (解決した課題・影響範囲) / evidence リンク。技術的難易度が高かったものはその理由も>

## コラボレーション・影響力

<レビューでの貢献、他メンバーの支援、議論のリード、チーム外との連携など行動面の evidence。具体的なスレッドや PR レビューへのリンクを付ける>

## 成長と対話で確認したい点

<期間内で見えた変化・成長の兆し。および、データからは判断できず 1on1 で本人に聞きたい点。断定ではなく問いの形で書く>

## データソースと制約

- 収集対象: <収集できたサービスと検索範囲>
- 未収集: <収集できなかったサービスとその理由>
- このレポートは業務システム上に記録が残る活動のみを対象としており、口頭でのコミュニケーション、DM、作成者の権限外のドキュメントは含まれない。活動の全体像ではない点に注意し、評価の唯一の根拠とせず本人との対話の材料として使うこと。
```

## 完了時

レポートのパスを伝え、サマリと定性ハイライトの要点を短く報告する。深掘りできなかった候補 (時間や権限の都合で読めなかったもの) があれば、追加調査できる旨を添える。
