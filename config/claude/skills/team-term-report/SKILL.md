# 半期振り返り資料の作成

エンジニアリングマネージャーが半期査定に使う振り返り資料を作成する。期初に設定した目標 (OKR) を起点に、期中の実績を証跡付きで Output として整理し、達成率の判断材料まで揃える。

実績の収集そのものは `team-activity-report` skill の手順を再利用する。この skill の役割は、収集した実績を **期初目標にマッピングし、査定で読まれる形式に構成すること** である。

## 原則

査定に直結する文書である。以下を必ず守る。

- **期初の目標設定なしに書き始めない**。Priority は期初に握った内容の転記であり、記憶や推測で埋めてはいけない。入力がなければユーザーに要求する。
- **達成率を AI が確定しない**。判断材料と案を提示し、確定はユーザー (評価者) が行う。案には必ず根拠を添える。
- **すべての Output に関連資料 (evidence) を付ける**。URL のない定性的な主張は書かない。実在を確認していない URL は絶対に書かない。
- **事実と解釈を区別する**。ログから言えることと、そこからの示唆を書き分ける。推測には推測と分かる表現を使う。
- **成果だけでなく過程を書く**。背景・課題・打ち手・成果のストーリーを書く。運や他者の主導で達成したものを、本人の成果として盛らない。
- **分業は担当領域を明記する**。曖昧なまま本人の成果に含めない。
- **未確認事項を隠さない**。可視データから判断できない点は、資料末尾に確認事項として列挙する。

## 手順

### 期初の目標設定を受け取る (必須)

最初に必ずこれを行う。目標設定が手元にない状態で収集や執筆に進んではいけない。

受け取り方は [references/goals.md](references/goals.md) に従う。要点は次の 3 つ。

- Objective と KR (`O1-KR1` などの番号とタイトル) をすべて拾う
- KR ごとに P0 (達成率 80% 相当) / P1 (100% 相当) / P2 (120% 相当) の記述を拾う
- キャリアラダーの対象等級 (例: 専門性 JB06) と、期初に置いたアクションを拾う

取り込んだ内容は作業用に保存し、Priority 欄はここからの転記のみで埋める。未定義の Priority は `未定義` とそのまま書く。

### 対象と期間を確定する

- **対象メンバー**: `team-activity-report` の `roster.local.md` を確認する。ID が未解決なら同 skill の「メンバー ID の解決」に従う。
- **対象期間**: 開始日と終了日を YYYY-MM-DD で確定する。会計年度に依存する期間表現 (上期・下期) は具体的な日付でユーザーに確認する。
- **執筆時点**: 期末前に書く場合、Output は見込みを含む。「今期達成見込み残タスク」「今期未達見込み残タスク」の欄はこの前提で埋める。期末後に書く場合は見込みではなく確定した実績として書き、残タスク欄も実績ベースで埋める。

### 実績を収集する

すでに `team-activity-report` のレポート (デフォルトは `~/Documents/activity-reports/`) があれば、それを一次入力として読み込み、不足分だけ追加収集する。なければ `team-activity-report` skill の収集手順 (`references/` 配下) に従って収集する。

この skill 固有の収集の重点:

- **KR に紐付く証跡を優先して深掘りする**。期初目標のキーワード (システム名・技術名) で GitHub Issue / PR、esa、Drive、Notion を検索し、KR ごとに証跡を束ねる。
- **定量値を拾う**。処理量、削減額、レイテンシ、適用範囲 (n サービス / n Workload)、負荷試験の到達値など。Output の説得力はここで決まる。
- **周知・全体適用の証跡を拾う**。設計や実装だけでなく、ドキュメント公開、他チームへの展開、合意形成のスレッドを探す。全体適用が Priority に含まれる場合、これが達成の根拠になる。
- **どの KR にも紐付かない大きな仕事を拾う**。障害対応、セキュリティインシデント、コスト最適化、他チーム支援などは「OKR 外 (SPOT 対応)」に入る。
- **キャリアラダーの証跡を拾う**。登壇資料、資格取得、執筆、社内外への技術発信、レビューを通じた他者育成。

### 期初目標と実績を突き合わせる

KR ごとに、期初の Priority と実際に行われた Action を並べ、差分を洗い出す。

- Priority どおりに進んだもの
- Priority にあったが着手されなかった / 中断されたもの
- Priority になかったが実施されたもの

**差分の理由は評価の要点である**。可視データから理由が読み取れない差分は、次のステップでユーザーに確認する。

### ユーザーに確認する

執筆前に、判断が必要な点をまとめてユーザー (評価者) に問う。ここを飛ばして推測で埋めない。

- Priority と実 Action の差分の背景 (方針転換の理由、上長との合意の有無)
- 分業が発生した仕事の担当領域の切り分け
- 可視データに出ない貢献 (口頭での支援、DM、社外折衝、他部署調整)
- 達成率の案に対する承認または修正
- キャリアラダーの対象等級と、その等級で期待される行動の解釈

確認事項が多い場合は、先に資料のドラフトを書き、該当箇所を `要確認:` として明示したうえでまとめて問うほうが効率がよい。

### 執筆する

フォーマットと各欄の書き方は [references/format.md](references/format.md) に従う。骨組みは [assets/template.md](assets/template.md) をコピーして使う。

文章は CLAUDE.md の Markdown 整形ルール (和欧文間の半角スペース、水平区切り線を使わない、見出しに通し番号を付けない、絵文字を使わない) に従う。ただし `[Priority]` `[Action]` などのラベルは提出先の様式なので、この表記のまま維持する。

保存先はデフォルトで `~/Documents/term-reviews/<メンバー名ローマ字>-<期の表記>.md` (例: `taro-yamada-2026H1.md`)。ディレクトリがなければ作る。ユーザーが別の場所を指定したらそちらに従う。個人の評価情報を含むため、リポジトリ内には保存しない。

### 完了時

- 保存先パスを伝える
- KR ごとの達成率の案と根拠を短く報告し、確定はユーザーの判断であることを明示する
- 資料内の `要確認:` 箇所と、証跡が薄い Output を列挙する
- 収集できなかったサービスや権限で見えなかった範囲を伝える
