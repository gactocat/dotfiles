# 振り返り資料のフォーマットと書き方

提出様式に合わせるため、`[Priority]` `[Action]` `[Output]` `[関連資料]` などのラベルはこの表記のまま出力する。骨組みは [../assets/template.md](../assets/template.md) を使う。

## 全体構成

```
# 振り返り資料

## 個人目標
### O1-KR1: <KR タイトル>     ← KR ごとに 1 節
### O1-KR2: <KR タイトル>

## OKR 外 (SPOT 対応)

## キャリアラダー
### <領域> <等級>              ← 例: 専門性 JB06
```

Objective が複数ある場合は `O2-KR1` 以降も同じ形式で節を並べる。

テンプレート冒頭のメタ情報行と、末尾の `## 確認事項` / `## データソースと制約` は手元で管理するための補助であり、提出様式には含まれない。提出先の様式へ貼るときは外す。

節ごとに置くラベル:

| ラベル | 個人目標 (KR) | OKR 外 | キャリアラダー |
| --- | --- | --- | --- |
| `[Priority]` | あり | なし | なし |
| `[Action]` | あり | あり | あり |
| `[Output]` | あり | あり | あり |
| `[関連資料]` | あり | あり | あり |
| `[達成率]` | あり | なし | なし |
| `[今期達成見込み残タスク]` | あり | なし | なし |
| `[今期未達見込み残タスク]` | あり | なし | なし |

## 各欄の書き方

### Priority (KR のみ)

期初に定めた目標設定からの**転記**。

```
P0: 期初に定めた達成率 80% に対応するアクション内容
P1: 期初に定めた達成率 100% に対応するアクション内容
P2: 期初に定めた達成率 120% に対応するアクション内容
```

- 原文を要約・言い換えせずに転記する
- 期初に設定がない段は `未定義` と書く
- 実際の Action が Priority と違っていてもよい。むしろ変わるのが普通で、**変わった理由に評価ポイントが隠れている**。差分は Output か残タスク欄で説明する

### Action

時系列で実施したアクションを**簡潔に箇条書き**する。番号付きリストにする。

- Priority と 1:1 で対応していなくてよい
- ダラダラ書かない。この一覧だけで期の全体像が掴めるようにする
- 1 項目が長くなるなら 2 項目に分割できるサイン
- 逆に対応する Output が長くなりすぎたら、Action の分割を検討する
- 目安は KR ごとに 2〜5 項目

### Output

Action の番号に対応させ、詳細を書く。番号は Action と厳密に一致させる。

**背景 → 課題 → 実施内容 → 成果**のストーリーで書く。

- 何を達成したかだけでなく、どのような背景と課題があり、どう戦略を立てて動いたのかを書く。**成果に至る過程も評価対象**である
- 定量的に書く。処理量、削減額、レイテンシ、適用範囲、負荷試験の到達値など
- 複数人で分業した場合は**担当領域を明記**する。書式は末尾に `(<氏名>: 設計/ドキュメント/周知、<氏名>: 検証/構築)` のように添える。チーム内で相互レビューした程度なら書かなくてよい
- 期末前に書く場合、見込みは見込みと分かる書き方にする
- 1 項目 200〜400 字程度を目安にする
- 次のようなケースは、成果が出ていても高く書かない。事実として書き、評価はユーザーの判断に委ねる
  - 戦略的な動きがなく、結果的に達成できた
  - 他者が主導した仕事を実行しただけ
  - 成果の因果が本人の打ち手と結びついていない

### 関連資料

Output の根拠となる資料を、**Output の番号に対応させて**列挙する。

```
1. 全体周知用ドキュメント「<タイトル>」 https://example.com/posts/1
1. 導入に向けた障壁の解消 https://github.com/<org>/<repo>/issues/1
2. 負荷計測ダッシュボード https://example.com/d/xxxx
```

- 番号は Output 番号を指す。同じ番号が複数行あってよい。連番にしない
- 資料タイトルと URL を併記する。URL だけを貼らない
- **エビデンスは必ず記載する**。定性的な説明より、定量が見える資料 (ダッシュボード、計測結果、Issue、PR) を優先する
- 実在を確認した URL のみ書く。URL を推測して組み立てるのは禁止
- 提出できる資料がない Output は、証跡が薄いことをユーザーに報告する

### 達成率

```
100% (個人目標の P1 相当を完了見込み)
120% (個人目標の P2 相当を達成)
```

- 数値と、どの Priority 相当かの根拠を括弧で添える
- **AI が確定しない**。案として提示し、ユーザーの承認を得てから確定値として書く。未承認の間は `要確認:` を添える

### 今期達成見込み残タスク / 今期未達見込み残タスク

- 残っていなければ `なし`
- 未達分は、なぜ未達なのか、上長との合意があるか、次期にどう繋げるかを書く。Output で触れた内容と重複してもよい

## 記述例 (匿名化)

```markdown
### O1-KR1: <対象システム> におけるベストプラクティスの全体適用

[Priority]

P0: 安全な終了処理方法の合意を得て、全体適用が完了している
P1: <機能 A> の有効化によるゾーン間トラフィックの軽減を実現
P2: 未定義

[Action]

1. 安全な終了処理方法の周知および全体適用
2. Endpoint 情報の公開先制御方法の周知および部分適用
3. <機能 A> 活用に向けた調査

[Output]

1. 従来手法は Application と Sidecar の両方に複雑な設定が必要で、不適切な設定によって安全な終了処理ができていない課題があった。新しいバージョンで導入された <設定項目> を利用して Sidecar 側の設定を簡略化する方針を立て、検証した。導入の障壁を解消したうえで Cluster 全体の初期値として有効化し、全 Workload を既存手法から新手法へ置き換え完遂した。

2. Sidecar の Memory 使用量は本番環境が開発環境の約 3 倍で、初期値では全 Namespace に Endpoint 情報を伝搬するため Replicas 規模に比例して増加していた。単一 Namespace で完結する Workload が存在することを踏まえ、公開先を制御する方法を調査・確立した。適用により大幅な削減が見込めるため、影響の大きいチームから順に適用を進めている。

3. <機能 A> の有効化により同一ゾーン内の通信を優先でき、遅延削減とコスト最適化が期待できる。ただしゾーン障害から回復した際に Pod のゾーン偏りが解消されない問題があり、可用性を担保するには Node の Descheduler を含めた設計が必要と判明した。<前提作業> の完了後に設計を再開することを上長と合意した。

[関連資料]

1. 導入に向けた障壁の解消 https://github.com/<org>/<repo>/issues/1
1. 全体周知用ドキュメント「安全な終了処理」 https://example.com/posts/1
2. 全体周知用ドキュメント「Endpoint 情報の公開先制御」 https://example.com/posts/2

[達成率]

100% (個人目標の P1 相当を完了見込み)

[今期達成見込み残タスク]

なし

[今期未達見込み残タスク]

<機能 A> の活用は <前提作業> の完了後に検討することを上長と合意した
```
